# v0.5 container interoperability plan

## Scope and sequence

1. **Qualify the drivers.** Build isolated probes against pinned LibDsk 1.4.2. Its source includes IMD and JV3 drivers with create, write and format paths. Probe those paths, enumerate sector IDs and status, and check whether comment and density metadata survive close/reopen. The pinned driver tree has no DMK driver. Review David Keil's format documentation and xtrs behavior, then evaluate a license-compatible existing implementation against a small native DMK adapter. Bring dependency or architecture changes back for approval.
2. **Define the sector mapping.** Keep Qt → Python broker → isolated C helper and cpmtools as the filesystem authority. Record physical track, head, sector ID, byte length, density, and available read status. Map each required sector to one byte offset in the RAW representation expected by the selected diskdef. Establish side ordering and sector-ID base from verified geometry and fixtures. Preserve diskdef offsets and reserved tracks. Apply skew through cpmtools exactly once. Use the inverse mapping for encoding. Reject ambiguous IDs, missing required sectors, unsupported sizes or layouts, and unrepresentable status or metadata before permitting writes. Retain the 128 MiB working limit.
3. **Integrate IMD, JV3, then DMK.** Decode into a private RAW session, expose container geometry and limitations, and encode a separate output for Save or Save As. Validate by reopening the staged container and comparing mapped RAW bytes and required metadata before publication. For IMD, preserve existing comment bytes unless explicitly edited in Image Information; include edits in dirty state and Discard. Qualify JV3 directory limits and density/deleted-data/error flags. For DMK, qualify ordinary FM/MFM tracks, ID offsets, CRCs and data marks; reject layouts whose reconstruction cannot be verified. Generate output containers from existing images; blank filesystem creation and formatting remain v0.6.
4. **Investigate the Amstrad sidecar.** The existing cpmtools Amstrad boot-superblock reader already resolves sector length, tracks, sectors per track, block size, directory size, reserved tracks, skew, extent factor, and CP/M 3 semantics. A standalone diskdef can plausibly be serialized from that resolved state under a different identifier, since `amstrad` dispatches to the built-in reader. No second boot or filesystem parser is required. Compare generated definitions against unmodified cpmtools on representative single/double-sided and PCW16 cases, including reserved bytes, listings and exported contents. Qualify container side ordering separately. Retain the explicit unsupported error until those comparisons pass.
5. **Qualify and review.** On macOS ARM64, use independently sourced and synthetic fixtures with unique sector markers, nontrivial skew, multiple sides, final-track files and damaged/malformed variants. For each container verify container → RAW using unmodified cpmtools listing and byte comparison, RAW → container → RAW equality, and edit → Save → reopen with expected sectors and metadata changed. Use independent tools or emulator reads to catch symmetric codec errors. Mount JV3 and DMK in xtrs or SDLTRS with a compatible CP/M guest; list, read and write a scratch disk, then reopen it with CP/M Image. For IMD, qualify against ImageDisk and select an emulator that supports the chosen IMD fixture directly, documenting any external conversion as a separate check. Test boot only on known bootable fixtures. Run targeted Windows and Linux ARM64 smoke at milestone completion and platform-specific tests when warranted. Record x86-64 as untested unless exercised.

## Publication requirements

Reuse v0.4 working copies, write confirmation, native ownership, hard-link Save As policy, source identity and fingerprint checks, staged validation, and journaled image/FDF publication. Backup rotation starts after required outputs are durable. Exercise failed encoding, stale sources, backup preparation and rotation failures, process interruption, sidecar conflicts, and Save As ownership transfer with disposable images. Container or comment changes must follow the same dirty-state and recovery rules as filesystem edits. Explicitly report any supported conversion that loses nonessential metadata.

Batch text export conversion remains deferred file-management work.


## Approved mapping decision

Use optional physical profiles with a default track layout and explicit per-track exceptions. Profiles supply only missing physical facts. A disk definition can be paired with multiple verified physical layouts. Keep CP/M skew and translation in cpmtools and standalone FDF files unchanged.

Use pinned LibDsk sector I/O for IMD and JV3. Preflight IMD headers independently because the generic LibDsk sector-ID enumeration collapses duplicate IDs. The dedicated DMK adapter is limited to verified container layouts and does not interpret the CP/M filesystem. Reject RAW-to-container writes unless the physical mapping is known and verified against the selected disk definition.
